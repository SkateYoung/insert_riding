# 项目更新日志
## 2026-07-15 远期订单匹配窗口可配置

### 变更内容

- 订单池匹配新增远期预约单释放规则：订单期望上车时间距离下单时间超过阈值时，先保留在订单池中暂不匹配。
- 默认超过 1 小时的订单视为远期订单，并在期望上车时间前 30 分钟释放到匹配流程。
- 多运营区匹配循环同步使用该规则，远期订单到释放时间前不会进入本运营区车辆候选评估。
- 新增 `GET/POST/PUT /admin/dispatch/matching-window-config`，支持运行时查看和调整远期阈值、提前释放时间。
- 配置当前为内存运行时配置，服务重启后恢复代码默认值。

## 2026-07-14 司机端接收确认后再进入 waiting_pickup

### 变更内容

- 订单匹配成功后先进入 `matched`，车辆路线临时占用并推送平台；平台确认司机端收到后才进入 `waiting_pickup`。
- 新增 `POST /orders/<request_id>/driver-push-confirmation`，支持平台回传 `received=true/false`。
- `matched` 待确认期间车辆仍可继续接新单；待确认订单继续保留在车辆计划路线中并参与容量/路线评估。
- 算法端不再执行 60 秒超时计时；司机端未收到、平台推送超时等情况统一由平台调用确认接口并传 `received=false`。
- 平台回传某个订单未收到时，只移除该订单的 O/D 步骤并退回 `order_pool`，同车其他订单和后续插单路线保留。
- `answer_time` 改为司机端确认收到派单时写入，匹配待确认阶段不再提前更新。
- 单车导航推送改为订单级待确认事件队列，连续接单时不会互相覆盖；payload 保留确认请求订单号和路线版本，不再包含算法端确认截止时间。

## 2026-07-13 新增运营区 SHP 编码自动尝试

### 变更内容

- `CityGraph` 加载 SHP/DBF 时支持多编码尝试：优先使用传入的 `shp_encoding`，默认从 `utf-8` 开始，失败后依次尝试 `gb18030`、`gbk`、`cp936`、`gb2312`、`big5`。
- 新增运营区入库前预加载时会使用同一套编码尝试；如果所有候选编码都无法解析，接口返回错误且不写入数据库。
- 预加载、初始化和加载测试成功后，会把实际成功的 `shp_encoding` 写回加载结果，后续初始化可优先使用成功编码。

## 2026-07-13 空车热点预测按运营区过滤并使用当前时间窗口

### 变更内容

- 空车热点预测读取历史完成订单时新增 `operation_area_id` 过滤，避免多个运营区订单混在一起稀释热点分布。
- 内存中的已完成订单样本也按 `operation_area_id` 过滤。
- 预测窗口从“最新历史订单时间 + 15 分钟”改为“当前系统时间 + 15 分钟”，并按 15 分钟时间片归一。
- 空车热点缓存有效性增加预测时间片校验，避免复用旧时间窗口的缓存。

## 2026-07-13 新增运营区失败不入库

### 变更内容

- `POST /admin/operation-areas` 改为先执行运行态预加载检查，再写入数据库。
- 如果 SHP 加载失败、状态无法进入运行态或其他预检查异常，接口返回错误且不会新增 `map_operation_area` 记录。
- 如果数据库写入后运行态兜底加载仍失败，后端会物理删除刚创建的运营区记录，避免留下半成品数据。
- 新增错误码 `operation_area_runtime_load_failed`，用于标识 SHP/运行态加载异常。

## 2026-07-09 运营区创建后自动加入运行态

### 变更内容

- 新增运行态加载入口 `state.load_operation_area_into_runtime()`。
- `POST /admin/operation-areas` 创建运营区后，如果运营区 `status='enabled'` 且 `audit_status='approved'`，后端会立即加载该运营区的 SHP。

- 接口响应新增 `runtime_load` 字段，用于前端判断是否已加入运行态、是否跳过或加载失败。
- 前端运营区保存后会展示运行态加载结果。

### 说明

- 本次运行态加载条件按启用状态和审核状态判断：`enabled + approved`。
- SHP 加载失败不会回滚已保存的运营区档案，会在响应和数据库加载状态中记录错误原因。

## 2026-07-09 多运营区 SHP 初始化、API 与前端管理落地

### 变更背景

在前置数据库结构已经支持“一个运营区对应一个 SHP 文件”的基础上，本次把系统初始化、运行态调度、管理接口和前端测试页接入多运营区逻辑。

### 后端运行态

- 新增 `state.city_maps`，按 `operation_area_code` 保存多个 `CityGraph`。
- 新增 `state.operation_area_records`、`state.default_operation_area_code`、`state.fleet_by_area`。
- 保留 `state.city` 和 `state.fleet` 作为默认运营区与全量车队兼容字段。
- `/init` 不再使用请求体中的 `shp_path`，改为读取 `map_operation_area` 中满足以下条件的运营区：
  - `deleted=0`
  - `is_deleted=0`
  - `status='enabled'`
  - `audit_status='approved'`
  - `load_on_startup=1`
  - `shp_path` 非空
- 如果没有生效运营区，初始化返回 `no_operation_area`，不加载 SHP，也不启动车队调度线程。
- 多个运营区会逐个尝试加载，单个 SHP 加载失败只写回该运营区 `load_status='error'` 和 `load_error`，不影响其他运营区。
- 至少一个运营区加载成功时，系统初始化成功，并把第一个成功加载的运营区作为默认运营区。

### 调度与数据隔离

- 订单、车辆运行态新增 `operation_area_code` 贯穿。
- 订单池匹配按运营区隔离，只在同一运营区内匹配车辆，不做跨运营区调度。
- 车辆路径更新、上下客确认、取消订单、高德优先重规划会根据车辆所属运营区选择对应 `CityGraph`。
- `/pois` 和 `/map/road-network` 支持 `operation_area_code` 查询参数。
- 初始化每个运营区时，会优先读取数据库中该运营区的 `map_poi` 站点并吸附到对应路网；如果数据库没有站点，则保留 SHP/路网自身 POI 兜底。

### 新增 API

- `GET /admin/operation-areas`
- `POST /admin/operation-areas`
- `GET /admin/operation-areas/<area_id>`
- `PUT /admin/operation-areas/<area_id>`

- `POST /admin/operation-areas/<area_id>/load-test`

### 前端测试页

- 支持查询、新增、编辑、软删除、测试加载运营区 SHP。
- 路线展示页新增当前运营区选择框。
- 手动/随机订单、POI 读取、车队读取、车辆新增/状态切换会自动带上当前运营区。

## 2026-07-09 多运营区 SHP 地图数据库模型准备

### 变更背景

当前业务进一步明确：

- 一个运营区对应一个 SHP 文件地图。
- 后续系统需要支持多个运营区同时运行。
- 系统初始化时应可通过查询运营区表，找到需要加载的 SHP 文件并构建对应路网。

本次继续只做数据库结构准备，不新增后端 API、不修改初始化代码、不改前端页面。

### 数据库变更

新增迁移文件：

- `database/20260709_add_operation_area_shp_scope.sql`

同步更新主建表文件：

- `database/bus_dispatch_core.sql`

扩展运营区表：

- 表名：`map_operation_area`
- 新增字段：
  - `shp_path`：SHP 文件路径
  - `shp_name`：SHP 文件名称
  - `shp_version`：SHP 地图版本
  - `shp_hash`：SHP 文件哈希
  - `shp_encoding`：SHP/DBF 编码，默认 `utf-8`
  - `coord_system`：坐标系，默认 `gcj02`
  - `load_on_startup`：系统启动时是否加载该运营区地图
  - `load_status`：地图加载状态，建议值 `pending/ready/error/disabled`
  - `load_error`：最近一次地图加载错误
  - `node_count`、`edge_count`、`poi_count`：地图统计信息
  - `bounds_json`：地图边界 JSON
  - `last_loaded_at`：最近一次地图加载时间

补充运营区归属字段：

- `map_road_node` 新增 `operation_area_id/operation_area_code`
- `map_poi` 新增 `operation_area_id/operation_area_code`
- `bus_vehicle` 新增 `operation_area_id/operation_area_code`
- `bus_order` 新增 `operation_area_id/operation_area_code`

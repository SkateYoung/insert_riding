# 综合成本函数说明

本文说明当前系统中 `CoreDispatcher.evaluate_route()` 的综合成本函数。该函数位于 `api/core.py`，主要用于在订单插入车辆路径时评估一条候选路线的优劣，成本值越低表示路线越优。

## 1. 函数定位

`evaluate_route(route, vehicle_state, on_board_orders, city_map, capacity, v_zone, original_etas)` 会模拟车辆按候选路线行驶后的时间、距离、上下客状态，并返回：

```python
(is_feasible, cost, arrival_times)
```

- `is_feasible`：候选路线是否满足硬约束。
- `cost`：综合成本分数，越小越好。
- `arrival_times`：各订单送达时间，用于后续计算老乘客延误。

该函数主要被 `_try_insert_order()` 调用。系统会尝试把新订单的起点 `O` 和终点 `D` 插入车辆现有 `planned_route` 的不同位置，然后用该成本函数选择最优插入方案。

## 2. 路线模拟过程

在计算成本前，函数会先按候选路线做一次时间线推演。

### 2.1 初始状态

使用 `vehicle_state` 中的字段作为起点：

- `time`：车辆当前业务时间戳。
- `last_node`：车辆当前所在路段起点。
- `next_node`：车辆当前所在路段终点。
- `progress`：车辆在当前路段上的进度，范围约为 `0~1`。

当前车上人数：

```python
current_load = sum(order.passenger_count for order in on_board_orders)
```

如果车辆正处于一条路段中间，还会计算剩余路段距离：

```python
first_step_dist = pass_dist * (1.0 - vehicle_state["progress"])
```

若当前车上无人，该距离计入 `empty_dist`；否则计入 `loaded_dist`。

### 2.2 路线逐段推演

对候选路线中的每个步骤：

- `step["type"] == "O"`：目标点为订单起点 `order.o_node`。
- `step["type"] == "D"`：目标点为订单终点 `order.d_node`。

通过路网最短路径计算距离：

```python
dist, path = city_map.get_path(current_node, target_node)
```

若不可达：

```python
return False, float("inf"), None
```

然后按当前载客状态累计距离：

- 当前载客人数为 0：计入 `empty_dist`。
- 当前载客人数大于 0：计入 `loaded_dist`。

时间推进：

```python
sim_time += dist / SPEED_MPS
```

当前速度使用 `SPEED_MPS = SPEED_KMH * 1000 / 3600`。代码中 `SPEED_KMH = 60`，因此实际速度约为 `16.67 m/s`。

### 2.3 硬约束

当前仍作为硬约束的条件：

1. 路段不可达：直接不可行。
2. 接客后载客人数超过车辆容量：直接不可行。
3. 送客后载客人数小于 0：直接不可行。

需要注意：当前代码已经不再把超出期望上车时间窗作为硬约束。过期订单仍然可以匹配，只会增加惩罚成本。

## 3. 成本组成

代码中综合成本被设计为四个维度：

```python
cost = (
    W_PASSENGER * passenger_cost
    + W_ENTERPRISE * enterprise_cost
    + W_SOCIAL * social_cost
    + W_FAIRNESS * fairness_cost
)
```

权重为：

```python
W_PASSENGER = 0.40
W_ENTERPRISE = 0.30
W_SOCIAL = 0.20
W_FAIRNESS = 0.10
```

但在当前实现中，`enterprise_cost`、`social_cost` 和 `fairness_cost` 最后都被置为 `0.0`，因此实际生效的是：

```python
cost = 0.40 * passenger_cost
```

下面分别说明四个维度。

## 4. 乘客体验成本

乘客体验成本是当前真正生效的核心成本。

### 4.1 候车时间成本

当车辆到达订单起点 `O` 时，记录接客时间：

```python
pickup_times[order.request_id] = sim_time
```

候车时间：

```python
wait_time = pickup_times[order.request_id] - order.req_time
```

候车成本：

```python
passenger_cost += wait_time * BETA
```

其中：

```python
BETA = 4.0
```

含义：乘客从下单到被接到的等待时间越长，成本越高。

### 4.2 期望上车时间超时惩罚

订单中保存了最晚上车时间：

```python
order.max_pickup_time
```

若车辆预计接客时间晚于该时间，不再拒绝匹配，而是计算有限惩罚：

```python
late_pickup_time = max(0.0, pickup_time - order.max_pickup_time)
passenger_cost += late_pickup_time * SLA_LATE_PENALTY
```

当前参数：

```python
SLA_LATE_PENALTY = 1.0
```

含义：积压订单或过期订单仍可继续匹配，但越晚接到，成本越高。

### 4.3 车内时间成本

当车辆到达订单终点 `D` 时，记录送达时间：

```python
arrival_times[order.request_id] = sim_time
```

车内时间：

```python
start_service_time = pickup_times.get(order.request_id) or order.actual_pick_time or vehicle_state["time"]
in_car_time = arrival_times[order.request_id] - start_service_time
```

车内时间成本：

```python
passenger_cost += in_car_time * GAMMA
```

当前参数：

```python
GAMMA = 3.0
```

含义：乘客上车后在车内停留越久，成本越高。该项会自然惩罚绕路和过长行程。

### 4.4 送达超时惩罚

订单中有估算的最晚送达时间：

```python
order.max_arrival_time
```

当前计算方式在 `Order` 中：

```python
max_arrival_time = max_pickup_time + direct_time * 2.0 + 300.0
```

也就是：最晚上车时间 + 直达时间的 2 倍 + 300 秒缓冲。

若预计送达晚于该时间：

```python
late_arrival_time = max(0.0, arrival_time - order.max_arrival_time)
passenger_cost += late_arrival_time * SLA_LATE_PENALTY
```

含义：送达超时不再导致路线不可行，只增加成本。

### 4.5 老乘客延误成本

当车辆上已经有乘客时，插入新订单可能导致老乘客延误。系统会先计算原路线的预计送达时间 `original_etas`，再比较插单后的送达时间。

延误时间：

```python
delay_time = arrival_times[order.request_id] - original_etas[order.request_id]
```

若 `delay_time > 0`：

```python
passenger_cost += delay_time * GAMMA
```

若老乘客延误超过 180 秒：

```python
passenger_cost += THETA
```

当前参数：

```python
THETA = 1500.0
```

含义：保护已经上车的乘客，避免新订单插入导致老乘客被严重绕路。

## 5. 企业效益成本

企业效益成本当前有计算逻辑，但最终被置零，暂未真正参与最终成本。

### 5.1 里程利用率惩罚

总模拟距离：

```python
total_sim_dist = empty_dist + loaded_dist
```

载客里程利用率：

```python
mileage_util_rate = loaded_dist / total_sim_dist
```

里程利用率惩罚：

```python
mileage_penalty = (1.0 - mileage_util_rate) * 1000.0
```

含义：空驶比例越高，成本越高。

### 5.2 满载率惩罚

本次路线服务的总乘客数：

```python
total_pax = 当前车上乘客数 + 路线中所有 O 步骤的乘客数
```

满载率：

```python
load_rate = min(1.0, total_pax / capacity)
```

满载率惩罚：

```python
load_penalty = (1.0 - load_rate) * 800.0
```

含义：车辆利用率越低，成本越高。

### 5.3 当前实际状态

虽然代码计算了：

```python
enterprise_cost = mileage_penalty + load_penalty
```

但随后又执行：

```python
enterprise_cost = 0.0
```

因此企业效益成本目前不影响最终派单结果。

## 6. 社会效益成本

社会效益成本当前也有计算逻辑，但最终被置零。

### 6.1 路权和碳排放代理成本

使用总行驶距离作为道路占用、能耗和碳排放的代理：

```python
total_dist = empty_dist + loaded_dist
```

基础社会成本：

```python
total_dist * 1.0
```

### 6.2 跨区惩罚

如果候选路线中的目标点不在车辆所属运营区：

```python
cross_zone_penalty += 300.0
```

社会成本设计为：

```python
social_cost = total_dist * 1.0 + cross_zone_penalty
```

### 6.3 当前实际状态

代码随后执行：

```python
social_cost = 0.0
```

因此社会效益成本目前不影响最终派单结果。

## 7. 平台公平成本

平台公平成本当前只保留了设计注释，没有实际计算。

注释中的思路是：

```python
fairness_cost = len(on_board_orders) * 500.0
```

含义：车辆已有订单越多，越不倾向继续给它派单。

当前实际代码：

```python
fairness_cost = 0.0
```

因此平台公平成本目前不影响最终派单结果。

## 8. 当前成本函数的实际效果

综合以上逻辑，当前真正影响路线选择的是：

1. 乘客候车时间。
2. 超出期望上车时间的有限惩罚。
3. 乘客车内时间。
4. 超出估算最晚送达时间的有限惩罚。
5. 老乘客被插单后产生的延误。
6. 老乘客延误超过 180 秒后的额外惩罚。

当前不会影响路线选择的是：

1. 空驶率。
2. 满载率。
3. 总行驶距离。
4. 跨区调度。
5. 车辆之间的公平分配。

这是因为企业效益、社会效益和公平成本均被置零。

## 9. 改进建议

### 9.1 输出成本明细，便于调试

建议让 `evaluate_route()` 可选返回成本明细，例如：

```python
{
    "passenger_cost": ...,
    "wait_cost": ...,
    "late_pickup_cost": ...,
    "in_car_cost": ...,
    "late_arrival_cost": ...,
    "old_passenger_delay_cost": ...,
    "enterprise_cost": ...,
    "social_cost": ...,
    "fairness_cost": ...
}
```

这样可以快速判断订单为什么没有被分给某辆车，也方便后续调参。

### 9.2 统一成本单位和归一化

当前多数成本直接以“秒”或“米”为基础相加，不同维度量纲不统一。建议先归一化，再加权，例如：

- 时间成本按分钟计算。
- 距离成本按公里计算。
- 载客率、空驶率按 `0~1` 比例计算。
- 每个维度映射到相近范围，例如 `0~100`。

否则某一项可能因为数值尺度过大而压制其他成本。

### 9.3 恢复企业效益成本，但先降低权重

企业成本目前被置零。建议先以较低权重启用：

```python
enterprise_cost = mileage_penalty + load_penalty
```

但需要先调小基数，例如：

- `mileage_penalty` 基数从 `1000` 调到 `100~300`。
- `load_penalty` 基数从 `800` 调到 `100~300`。

避免企业成本突然压过乘客体验成本。

### 9.4 将“绝对成本”改为“增量成本”

当前路线成本更接近候选路线的绝对成本。插单场景中，更合理的是比较新路线相对原路线增加了多少成本：

```python
incremental_cost = new_route_cost - original_route_cost
```

这样可以避免长路线车辆天然成本高、短路线车辆天然成本低造成偏差。

### 9.5 对严重过期订单使用非线性但有限的惩罚

现在过期订单的惩罚是线性的：

```python
late_time * SLA_LATE_PENALTY
```

建议改为分段函数：

- 0~10 分钟：低惩罚。
- 10~30 分钟：中等惩罚。
- 30 分钟以上：高惩罚，但仍不禁止匹配。

这样既满足“乘客未取消就继续服务”的业务要求，也能避免极端积压订单完全压制新订单。

### 9.6 引入乘客等待意愿或取消概率

长期积压订单不应被禁止，但可以引入“取消风险”：

```python
cancel_risk = f(wait_time)
```

等待越久，取消风险越高。系统可以优先处理高风险订单，但不必把它们视为不可行。

### 9.7 使用动态速度

当前所有路径都使用固定 `SPEED_MPS`。实际路网中，不同时段、道路等级、拥堵情况会显著影响 ETA。建议逐步引入：

- 按时间段的速度。
- 按路段的速度。
- 基于历史交通状态的速度修正。

### 9.8 改进公平成本

公平成本不建议只看 `len(on_board_orders)`，可以考虑：

- 车辆最近一小时接单数。
- 车辆最近一小时载客里程。
- 司机连续驾驶时间。
- 车辆空闲等待时间。
- 车辆所在区域供需紧张程度。

这样公平性会更接近真实运营调度。

### 9.9 保留硬约束，但不要滥用

建议只把以下情况作为硬约束：

- 路网不可达。
- 车辆容量超限。
- 送客发生在接客之前。
- 车辆正在休息或收车中。

时间窗、绕路、跨区、空驶等更适合作为软约束成本，而不是一票否决。

### 9.10 参数配置化

当前参数写死在函数内部：

```python
BETA = 4.0
GAMMA = 3.0
SLA_LATE_PENALTY = 1.0
THETA = 1500.0
```

建议后续迁移到配置文件或接口参数中，至少支持：

- 本地测试调参。
- 不同城市、不同车辆类型采用不同参数。
- 线上灰度实验。

## 10. 建议优先级

建议按以下顺序改进：

1. 增加成本明细输出，先解决可解释性问题。
2. 将企业效益成本恢复为可配置软成本。
3. 对各成本做归一化，避免尺度失衡。
4. 将插单评估改为增量成本。
5. 引入动态速度和真实运营公平指标。

其中第 1 步风险最低，也最利于后续定位问题；第 4、5 步涉及调度策略变化，建议在测试脚本和前端可视化都稳定后再做。
